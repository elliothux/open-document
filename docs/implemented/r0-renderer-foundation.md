# R0 通用渲染架构与薄 Renderer

状态：`implemented`，2026-10-14。首次落地完成 DOCX 与 Web Canvas；其他格式和平台尚未接入，未验证性能收益。

MoonBit/WASM 输出定位后的绘制指令，平台 Renderer 执行绘制。内容与交互覆盖层独立更新。内部布局继续负责命中、选区和 PDF，宿主保留输入顺序、资源接入与生命周期。

[P4 DOCX 编辑](p4-docx-editing.md)是首个接入场景。当前支持的正文、单个表格单元格编辑及文字、表格、内联图片沿此路径呈现。核心/宿主职责归 [SDK 合同](../references/sdk.md)，实际 API 与边界归[格式合同](../references/formats.md#通用绘制输出)，执行方法归[测试说明](../references/testing.md)。

## 通用合同

Renderer 指绘制执行器。绘制区域指一次输出对应的页面、幻灯片或视口范围。绘制区域不必对应完整文档或工作表。平台画布、事件队列和平台资源由宿主拥有。

```text
平台输入 → 格式核心 → 布局与绘制输出 → 宿主调度 → 平台 Renderer
                  → 命中与选区几何 → 宿主交互覆盖层
                  → 文字与对象语义 → 平台输入及无障碍接入
```

| 所有者 | 职责 |
| --- | --- |
| 格式核心，MoonBit/WASM | 文档语义、编辑、计算和格式保存；生成排版输入 |
| 共享布局与绘制底座，MoonBit/WASM | 塑形、几何、绘制指令、资源引用和复用；保留各格式所需的布局算法 |
| 宿主适配层 | 调用核心，校验批量输出、资源引用和错误；Web 使用 TS/Worker |
| 平台呈现与输入 | 调度、输入顺序、焦点、剪贴板、可见区域、缩放和资源释放 |
| 平台 Renderer | 将指令映射为绘图调用，复用平台资源对象 |

核心统一输出绘制区域内的 point 坐标。坐标原点在左上，x 向右、y 向下。格式核心负责源单位转换；宿主在绘制入口应用视口变换、缩放和设备像素比（DPR）。Renderer 不重新选择字体、塑形、换行或计算编辑位置。

`Path2D`、`ImageBitmap` 和 Canvas 留在 Web。核心合同只包含数值、文字、绘制指令和资源标识。批量数据合同独立于 JSON、Worker 或其他传输方式。新宿主可以替换传输与绘图接入，无需重写文档算法。

### 绘制、交互与语义分开输出

绘制输出只包含尺寸、顺序、坐标、样式和资源引用。Renderer 按顺序执行，不出现按 DOCX/XLSX/PPTX 分支的格式规则。

命中、光标、选区及对象操作位置由核心查询返回。文字、阅读顺序和对象语义单独供宿主使用。宿主不从像素反推文档内容，也不维护第二份可编辑模型。

第一版表达当前已有的绘制能力。后续格式需要路径、变换或新效果时，在同一合同中增加具体指令，并同步更新实际使用的后端。未知指令明确报错，不静默跳过。无需预建指令插件注册系统。

### 复用与失效遵循相同规则

核心决定数据是否变化，宿主决定何时呈现。各格式复用以下分工：

| 可复用结果 | 决策位置 | 失效依据 |
| --- | --- | --- |
| 塑形和布局 | 核心 | 内容、字体、样式、可用空间等实际依赖 |
| 绘制指令和资源引用 | 核心 | 布局结果、资源及绘制属性 |
| 字形路径和解码图片 | 平台资源层 | 核心资源身份与生命周期 |
| 区域像素 | 平台呈现层 | 核心绘制身份、缩放、DPR 与呈现参数 |
| 交互覆盖层 | 核心提供几何，宿主绘制 | 当前布局、选区与交互状态 |

文档版本、布局身份和绘制身份各有用途。画面相同不表示编辑几何相同。首次实现用布局身份保守地使画面失效；只有核心证明绘制结果相同，宿主才能跨布局复用像素。

固定纸张的缩放通常只改变呈现。网格视口或自适应布局改变时，宿主把新的范围交给核心。核心决定需要计算哪些内容，不把分页规则强加给所有格式。

后续按区域更新时，核心声明变化和删除的区域。初期使用独立完整区域结果；确需差分时再引入基线身份与重同步。宿主只合并可安全省略的中间呈现，已接受的编辑命令仍完整执行。

### 资源与平台适配

核心用稳定资源标识引用字体、字形和图片。身份覆盖会改变绘制结果的属性；资源内容改变时身份也应改变。平台资源缓存限定在所属会话内。

核心负责资源依赖与计算缓存上限。宿主负责平台对象的内存预算与释放。缓存被释放后，可以从核心或资源提供方重新取得数据；缺资源时明确失败。

平台获取文件和字体，提供当前依赖的平台图片解码。首期保持浏览器解码，并标明依赖。以后加入可移植解码器时，把解码计算放入核心；Renderer 始终只消费已准备的资源。

Web 可采用 Canvas 缓存、动画帧调度、Transferable 或 OffscreenCanvas。其他宿主使用各自的呈现机制。平台优化遵守相同的数据身份、更新和释放合同，不回流为格式专用逻辑。

### 后续格式的接入方式

| 核心 | 保留的格式职责 | 复用的绘制路径 |
| --- | --- | --- |
| DOCX | 段落、表格、分页与编辑范围 | 页面绘制区域，文字与选区输出 |
| XLSX | 单元格、公式、网格和视口几何 | 有界视口绘制区域，文字、线框与选区输出 |
| PPTX | 形状、层叠、幻灯片及对象编辑 | 幻灯片绘制区域，路径、文字与对象覆盖层 |
| PDF 输入 | 页面解释、文字与对象语义 | 页面绘制区域及查询结果 |

本表说明接入职责；DOCX 与 XLSX 的交付见对应阶段，其他格式尚未实现。各格式提供自己的输入、布局和编辑规则，共用底座中已经适用的计算与绘制能力。新平台实现资源、绘图和输入接入；WasmGC 运行能力单独核验。

## 首次落地结果

- [核心绘制输出](../../modules/layout/src/drawing.mbt)生成矩形、字形批次、图片及裁剪。轮廓和图片资源与区域分开，重复轮廓共用一份数据。
- Bridge 返回绘制批次与独立语义页。命中、选区和 PDF 继续使用内部 `Layout`。WASM 与主线程客户端校验指令、资源及布局身份。
- [CanvasRenderer](../../packages/web/src/drawing.ts)执行指令。旧的 TS 页面/行/run 遍历绘制路径已删除；预览和编辑共用 [PageCanvas](../../packages/web/src/page-canvas.ts)。
- 内容按布局身份、页码、缩放和 DPR 复用。编辑覆盖层单独清除和绘制，不截获指针事件。只有像素尺寸变化时重设画布尺寸；覆盖层计入原总预算。
- 图片资源身份绑定尺寸与像素。浏览器仍负责图片解码，关闭时释放位图、路径和画布。未知指令、缺资源和过期几何明确失败。
- 编辑队列、IME 候选、撤销、保存屏障和恢复保持。DOCX 保存读取核心文档，PDF 保留字体嵌入、文字映射、图片和裁剪。

采用 ONLYOFFICE [页面缓存与可见页绘制](https://github.com/ONLYOFFICE/sdkjs/blob/72b0421c0bbf9d01eed9cf14834ae47eb2df1b50/word/Drawing/HtmlPage.js#L3009)和[覆盖层](https://github.com/ONLYOFFICE/sdkjs/blob/72b0421c0bbf9d01eed9cf14834ae47eb2df1b50/word/Drawing/HtmlPage.js#L428)的职责分离机制。已核对固定源码和 AGPL-3.0 许可；本次实现复用本项目代码。

## 足够检查

根静态检查、release 构建和 API 生成通过。四项定向单元检查通过，覆盖绘制校验、资源缺失与依赖迁移；一项核心图片资源检查通过，覆盖稳定身份、替换和失败原子性。

Chromium 的 17 项现有功能用例分次通过，覆盖点击/拖选、空白页、缩放、DPR 2、正文与表格编辑、IME 候选/取消、停止恢复、关闭释放，以及文字/图片/裁剪的 Canvas 与 PDF 输出。拖选断言确认正文重绘为零，输入后重新绘制；原像素、源保留和 PDF 文字断言保持。

证据位于本地 `.temp/r0-renderer/`。原失败及修正后的局部结果保留。完整报告器按 219 项清单拒绝局部运行；后续定向检查使用标准报告器成功退出。旧布局几何拒绝及缩放超预算后的恢复也已验证。这些结果只证明所选用例，不代表完整 loop。未运行性能专项、其他浏览器、Windows/Word 或新增系统输入法验收。

## P5 接入

[P5](p5-xlsx-editing.md)已将绘制批次统一为 `regions` / `drawRegion`，抽出共用 `CanvasSurface`。DOCX 保留图片准备和分页语义，XLSX 提供核心网格语义。PDF writer 消费两种格式共有的 `PositionedDocument`，包含定位文字、glyph/Unicode、图形与页面；表格打印独立于屏幕视口。当前合同见[格式说明](../references/formats.md#通用绘制输出)。

## 后续能力的进入条件

| 已证实的需求 | 后续最小动作 |
| --- | --- |
| 完整结果传输阻碍当前文档交互 | 核心按页输出，只返回所需页面和资源；先不做指令级差分 |
| 当前页重复绘制仍造成卡顿 | 核心提供页面绘制身份；Web 按身份复用图像，几何仍绑定 layoutId |
| Canvas 绘制阻塞主线程输入 | 将同一 Renderer 移到 Worker/OffscreenCanvas，保持输入与绘制职责 |
| 产品需要连续多页视图 | 增加可见页选择和有界表面缓存 |
| P9 开始接入明确的新宿主 | 实现该宿主的绘图、资源和输入适配，单独核验 WasmGC 运行能力 |

这些能力沿用上文的通用合同，按实际需求实现，不作为首次落地的完成条件。本期不预建场景图、插件系统、GPU 后端、跨平台适配矩阵或自定义二进制协议。扩展性来自清楚的数据职责和单一实现路径。
