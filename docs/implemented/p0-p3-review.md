## 必须修复

### 1. 局部间距覆盖破坏继承的行高 — 高

位置：[段落属性解析](../../modules/formats/src/docx/properties.mbt)，第 182–228 行。

- **当前行为：** 解析器合并文档默认值、命名样式和直接格式，得到段落属性。
- **问题：** 解析器只根据当前元素的 `lineRule` 换算 `line`，却单独继承 `exact`。如果间距元素没有显式声明 `atLeast`，解析器还会把 `minimum` 重置为 0。浏览器复现中，段落仅修改段后距，继承的 30 pt 最小行高就变为 14.982 pt。继承固定行距后直接设置 `line=480`，解析器得到 2 pt 固定行高。
- **修复方向：** 先共同解析最终生效的行距规则和原始数值，再换算单位。仅修改段前、段后距时，解析器应保留继承的行距设置。内部表示应区分自动、固定值和最小值规则。
- **不修复的影响：** 普通样式覆盖会在用户没有要求改变行高时改变分页，甚至造成文字重叠。预览和 PDF 都会使用错误的布局几何。

待补回归：默认值和 `basedOn` 继承链均应覆盖以下情况。

- 仅修改段前或段后距。
- 仅修改行距数值。
- 仅修改行距规则。

测试应同时检查解析后的属性和下一段的位置。上述情况属于 P3 已承诺的样式继承范围，不是新增格式能力。[Open XML 行距说明](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.line?view=openxml-3.0.1) 描述了继承规则和不同规则对应的单位。

### 2. 自动换行丢失段落级双向文字上下文 — 高

位置：[行测量](../../modules/layout/src/paragraph.mbt)，第 18–29、195–245 行。

- **当前行为：** 断行器先塑形候选前缀，再按视觉顺序排列选定行。
- **问题：** 断行器把每个候选子串当作新段落，传给 `bidi.process`。复现输入是一个短段落：开头为阿拉伯文，后缀包含数字、标点和拉丁文。后缀前自动换行后，第二行的双向嵌入层级全部变为 0。断行器没有保留整段解析出的层级和视觉分组顺序。本次已在真实 Worker 中复现问题，输入不含显式方向控制字符或复杂文档结构。
- **修复方向：** 先解析整个段落的双向文字上下文，再对选定的行范围应用行级规则。片段塑形时保留已解析的层级；仅对每一行独立推断方向并传入，并不足以修复问题。
- **不修复的影响：** 改变页面宽度可能改变同一段文字的阅读顺序。后续选区和命中测试也会建立在错误的布局上。

待补回归：测试应覆盖从右向左（RTL）文字与数字/拉丁文后缀之间的自动换行。测试还应覆盖换行处的中性标点，以及跨多个源文字片段（run）拆分的等价文字。测试应使用独立的段落级判定器，不应调用同一个片段算法生成预期。[Unicode UAX #9](https://www.unicode.org/reports/tr9/#Resolving_Implicit_Levels) 明确区分段落解析与行级重排。

### 3. 固定行距没有约束所有行几何 — 中

位置：[段落行构建](../../modules/layout/src/paragraph.mbt)，第 264–277、305–316 行；Canvas 绘制（审查时的 `packages/web/src/foundation.ts`）的 `drawPage`。

- **当前行为：** 布局负责计算行高、基线，以及段尾手动换行后产生的空行。
- **问题：** 段尾空行分支使用 `line_height.max(size)`，覆盖了显式指定的较小固定行高。复现输入使用 11 pt 文字和 6 pt 固定行距。布局返回的文字行高为 6 pt，段尾空行高却为 11 pt。纯文字行的基线始终使用字体上升部度量，不随固定或最小行距改变。复现中的 6 pt 行，其基线位于行顶下方 11.759 pt。Canvas 和 PDF 两个渲染后端均没有行级裁剪指令。
- **修复方向：** 普通行和段尾空行使用同一套行度量规则。在共享布局/绘制数据中实现所选兼容配置要求的基线定位与裁剪，不分别在 Canvas 和 PDF 中补偿。
- **不修复的影响：** 手动换行会意外改变固定行距段落的高度；较小的固定行高还可能使文字绘制超出分页计算采用的区域。

待补回归：测试应覆盖固定行高小于和大于字体自然高度的情况。测试还应检查段尾手动换行、后续段落位置，以及 Canvas/PDF 裁剪结果。[Open XML 行距说明](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.line?view=openxml-3.0.1) 描述了行高不足或过大时的文字定位规则。段尾空行的高度不一致可独立观测，不依赖参考应用的栅格化结果。

### 4. 构建后的入口没有共享公开导出的错误类 — 中

位置：Web 构建配置（审查时的 `packages/web/package.json`），第 30 行；[Wasm 适配层构建配置](../../packages/wasm/package.json)，第 29 行；Worker 响应处理（审查时的 `packages/web/src/connection.ts`），第 2、24–32 行。

- **当前行为：** 调用方可从公开的 Wasm `foundation` 入口导入 `DocumentError`，再调用浏览器 `FoundationClient`。
- **问题：** 各入口独立打包，因此包含不同的错误类副本。Chromium 中真实的 `client.query()` 错误具有 `name=DocumentError` 和 `code=invalid-operation`。但调用方使用公开 `foundation` 模块导出的类检查 `error instanceof DocumentError`，结果为 `false`。原因是主线程中的构造函数身份不一致，不是 Worker 消息跨线程后丢失原型。
- **修复方向：** 通过共享构建产物或保留模块导入，让浏览器侧各入口在运行时使用同一个 `DocumentError` 定义。同时检查 `engine` 入口，该入口也打包了 `foundation` 实现。
- **不修复的影响：** 调用方常规的错误处理会漏掉 SDK 错误，把可恢复的文档失败当成未知失败。

待补回归：测试应同时导入实际构建后的公开入口，并触发真实文档错误。测试应同时检查类身份和错误字段。仅检查源码类型，或只检查 `name`/`code` 的测试，无法发现此问题。

## 建议修复

### 5. 已应用样式中的不支持属性缺少诊断 — 中

位置：[内容流诊断](../../modules/formats/src/docx/flow.mbt)，第 130–155、185–197 行；[run 属性解析](../../modules/formats/src/docx/properties.mbt) 的 `run_properties`。

- **当前行为：** P3 在保留原始 DOCX 数据的同时，对不支持的格式提供诊断。
- **问题：** 不支持属性的扫描只覆盖主文档树，没有覆盖从 `styles.xml` 实际应用的样式属性。复现中，段落使用含 `w:vanish` 的样式，但文字仍可见，诊断列表也为空。如果正文直接声明同一属性，现有扫描则会识别该属性。这是诊断缺口，不表示隐藏文字渲染已经属于支持范围。
- **修复方向：** 解析已应用的样式或默认属性块时，检查其中不支持的属性。诊断应标明所属部件和特性。不必扫描未使用的样式，也不必为此建立完整 schema 校验器。
- **不修复的影响：** 即使引擎丢弃了已应用样式中的特性，应用仍会收到看似没有问题的预览结果。

待补回归：测试应分别在直接格式、默认值和已使用的继承样式中声明同一不支持属性。测试还应加入未使用样式作为对照。引擎应先报告不支持的隐藏文字语义，应用再决定是否把结果呈现为保真转换。

### 6. 图片限制在浏览器解码之后才检查 — 中，源码确认的风险

位置：预览资源准备（审查时的 `packages/web/src/preview.ts`），第 79–93 行。

- **当前行为：** 浏览器解码嵌入图片，再向核心发送含红、绿、蓝和透明度通道的 RGBA 数据。核心按预算接收 RGBA 数据。
- **问题：** `createImageBitmap` 在尺寸和像素数检查之前执行。声明尺寸超限的编码图片会先进入解码器，再由尺寸检查拒绝。高压缩比的大尺寸位图可能消耗解码资源。后续 RGBA 预算无法阻止解码器消耗这些资源。本次没有分配超大图片，也没有演示内存耗尽崩溃。
- **修复方向：** 对明确支持的图片格式，在完整解码前校验声明尺寸和预计解码预算，并保留现有的解码后校验。保持核心与宿主的职责边界。不必引入第二套文档模型或通用编解码框架。
- **不修复的影响：** 当前资源合同只能限制核心接受的图片，不能作为浏览器超大图片解码的防护保证。

待补回归：测试应确认宿主在调用解码器前拒绝超尺寸编码图片。测试还应覆盖声明尺寸与实际尺寸不一致的情况。进程峰值内存是另一个尚未测量的边界。本项不表示核心 RGBA 计数有误。

## 需要裁定的参考差异

### 7. 相邻段落间距缺少明确的兼容策略 — 待裁定

位置：[正文分页](../../modules/layout/src/pagination.mbt)，第 120–144 行；[表格单元格分页](../../modules/layout/src/pagination.mbt)，第 191–207 行。

- **当前行为：** 分页分别累加前一段的段后距和后一段的段前距。
- **问题：** 10 pt 段后距接 12 pt 段前距，在 SDK 中贡献 22 pt 间距。[Open XML 间距规则及示例](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines?view=openxml-3.0.1) 描述了最大值规则。但 SDK 没有区分普通相邻段落、兼容设置和分页边界，不能仅凭这一条规则把所有累加替换成 `max`。
- **处理方向：** 兼容性和计算逻辑共同参考 ONLYOFFICE 与 LibreOffice。普通同页相邻段落的段前、段后距建议按最大值合并；兼容标志、同样式间距抑制和分页边界应分别定义规则。该建议仍需用固定版本参考引擎验证，不表示本次已经批准或实现新的兼容合同。
- **不处理的影响：** 无条件累加缺少适用范围，可能改变分页；无条件取最大值也可能破坏要求累加或特殊边界处理的文档。

2026-10-10 补充源码核对：

- **ONLYOFFICE：** 在 `sdkjs` 提交 `72b0421c0bbf9d01eed9cf14834ae47eb2df1b50` 中，`Paragraph.Get_CompiledPr` 保留前段的段后距，把当前段的段前距调整为 `max(Prev_After, Cur_Before) - Prev_After`。因此，在普通分支中，10 pt 与 12 pt 的合计贡献是 12 pt，而不是 22 pt。该方法另行处理 `ContextualSpacing`、自动间距、编号和表格边界，不能只摘取公式作为完整规则。[段落属性计算源码](https://github.com/ONLYOFFICE/sdkjs/blob/72b0421c0bbf9d01eed9cf14834ae47eb2df1b50/word/Editor/Paragraph.js#L10735-L10965)
- **LibreOffice：** 在 `core` 提交 `1746b16a564f59fcaf8c5670bb292748408da54e` 中，`SwFlowFrame::CalcUpperSpace` 在 `PARA_SPACE_MAX` 为真时累加段距，为假时取最大值，并另外处理上下文间距和行距。这个内部标志的名称不能按字面理解。DOCX 导入把 `doNotUseHTMLParagraphAutoSpacing` 映射到 `AddParaTableSpacing`，后者控制该标志。[布局分支](https://github.com/LibreOffice/core/blob/1746b16a564f59fcaf8c5670bb292748408da54e/sw/source/core/layout/flowfrm.cxx#L1582-L1770)、[DOCX 设置映射](https://github.com/LibreOffice/core/blob/1746b16a564f59fcaf8c5670bb292748408da54e/sw/source/writerfilter/dmapper/DomainMapper_Impl.cxx#L10234)、[内部标志映射](https://github.com/LibreOffice/core/blob/1746b16a564f59fcaf8c5670bb292748408da54e/sw/source/uibase/uno/SwXDocumentSettings.cxx#L444-L452)
- **既有运行证据的边界：** 本机 LibreOffice 开发版曾对精简输入表现为累加，但它不是 P3 冻结版本，也不是本次核对的源码提交。精简输入没有 `word/settings.xml`。目前没有证明该次运行实际走了哪个兼容分支，因此不能把这一结果概括为“LibreOffice 总是累加”，也不能断言差异已经定位到某个标志。

待补回归：

1. 在正文和同一表格单元格中，覆盖段后距小于、等于、大于段前距，以及任一侧为零的情况。分开断言解析属性、实际段间距离和分页结果，不把文字基线距离当作纯段距。
2. 分别覆盖 `settings.xml` 缺失、兼容标志缺省、显式关闭和开启；补充同样式的 `contextualSpacing`、自动间距及编号组合。未支持的设置应明确诊断，不静默套用普通规则。
3. 分开检查同页、自然跨页、显式分页，以及单元格首尾段落；不把同页公式直接推广到所有边界。
4. 优先参考 LibreOffice 的 `testN778140`（兼容标志相关的段距导入/往返）和 `testTdf145716_nonHTMLspacing`（带兼容标志的往返页数回归），再按 SDK 范围补精简断言。它们不直接证明上述 10/12 pt 样例的预期。[段距用例](https://github.com/LibreOffice/core/blob/1746b16a564f59fcaf8c5670bb292748408da54e/sw/qa/extras/ooxmlimport/ooxmlimport.cxx#L538-L549)、[分页用例](https://github.com/LibreOffice/core/blob/1746b16a564f59fcaf8c5670bb292748408da54e/sw/qa/extras/ooxmlexport/ooxmlexport25.cxx#L784-L792)

本项仍不计为已确认、可无条件改成 `max` 的缺陷。补充调查只核对了源码和既有输入，没有运行新的 ONLYOFFICE、LibreOffice 或 Microsoft Word 对照测试，也没有更新冻结的参考结果（golden）。兼容裁定应记录输入设置、参考版本及实际结果；上游源码参考不等于已经证明与 Microsoft Word 一致。

## 扩展产品前的缺口

以下属于下一阶段要求或已记录的限制，不追溯认定为 P0–P3 未完成。

| 缺口 | 当前证据 | 下一步 |

| DOCX 结构化编辑 | `Session.replace` 仅覆盖已有文本节点；没有范围编辑、段落拆分/合并或 DOCX 撤销历史 | P4 先建立位置/范围、原子命令、源内容保留和历史记录。P0 文本撤销不等于 DOCX 撤销。 |

| 更广的 Office/PDF 能力 | XLSX/PPTX 仍为占位模块；PDF 输出不等于 PDF 输入编辑 | 保持本报告编写时的 P5–P9 范围（当前编号见[路线图](../references/roadmap.md)），不为解决本报告的问题而提前建设通用抽象语法树（AST）、替换渲染器或多语言绑定平台。 |
