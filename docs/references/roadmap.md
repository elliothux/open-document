# 产品路线图

**当前目标：复刻 GenOffice 的文档、表格、PPT、PDF 全功能 SDK。** 本地 `references/genoffice` 是功能与 UI 交互参考，App 仅用于视觉对比验收和交互参考。Office 能力、布局、算法与兼容行为仍优先参考 ONLYOFFICE，其次 LibreOffice。完整目标与职责归 [SDK 合同](sdk.md)，源码差距见 [G3](../g3-genoffice-sdk-gap.md)。

项目未发布，当前有 0 个用户。按当前需求从 Day One 设计，可以直接修改最底层架构，只保留一条实现路径。兼容代码仅限文档格式。浏览器只覆盖 Chrome/Chromium，发布和规模化建设按真实需求安排。

2026-10-14 重排后，先补四类编辑器的核心功能，再扩大兼容与性能，接入外围能力，最后完成跨宿主。**功能优先级 P0/P1/P2 与阶段编号分开**：P0–P9 已完成限定范围，后续阶段为 P10–P16。

| 功能优先级 | 范围 | 对应阶段 |
| --- | --- | --- |
| P0 核心功能 | 可嵌入 SDK、默认 UI、文档操作、必要布局/计算、保存及常用转换 | P9–P13 |
| P1 兼容与性能 | 复杂文件/格式变体、布局/公式/效果覆盖、大文件和交互性能 | P14 |
| P2 次要与外围能力 | AI、协作、Diff、OCR、校对、证书等接入，以及次要宿主 | P15、P16 |

安全、保真、恢复、资源上限和无障碍随每个功能完成。使核心操作可用的布局、计算和格式支持属于 P0；不能以“兼容放 P1”为由留下不能保存的功能。卡死或无法交互的问题在阻塞的阶段处理。

## 后续阶段与顺序

| 阶段 | 用户结果 | 功能优先级 | 状态与依赖 |
| --- | --- | --- | --- |
| P10 DOCX 核心功能 | 创建并编辑格式、结构、页面、图文、引用和审阅内容，保存与输出 | P0 | `planned`；接入 P9，按操作增量交付 |
| P11 XLSX 核心功能 | 创建工作簿，完成常用计算、结构/格式、数据处理、图表与分析 | P0 | `planned`；接入 P9，复用 P10 已需要的共用绘制能力 |
| P12 PPTX 核心功能 | 创建图文演示，编辑母版/布局/对象，放映并输出 | P0 | `planned`；接入 P9，复用文本、图形和图表能力 |
| P13 PDF 核心功能 | 编辑内容、整理页面、批注/表单、脱敏与转换 | P0 | `planned`；接入 P9；PDF → Office 依赖 P10–P12 的创建与保存 |
| P14 兼容与性能 | 扩大真实文件覆盖，使复杂/大文件操作可用 | P1 | `planned`；围绕已交付功能和具体差距实施 |
| P15 次要与外围能力 | AI、协作、Diff、OCR、校对、证书与外部服务接入 | P2 | `planned`；逐项接入稳定的核心命令与输出 |

实施顺序为 P9 → P10 → P11 → P12 → P13 → P14 → P15 → P16，跨宿主作为最后一项需求。阶段内部每个完整操作可以独立交付。跨格式只等待实际依赖，不要求前一格式达到全部兼容才开始后一格式。P9 已接通现有能力，当前下一项是 P10。

### P9 Web SDK 与默认 UI（已完成）

用户结果：宿主加载公开构建产物，用普通 JS 挂载和释放编辑器。用户能通过默认 UI 完成当前已有的打开、编辑、撤销、缩放、保存和输出，明确看到不支持或只读的原因。

交付与足够检查归 [P9](../implemented/p9-web-sdk-ui.md)。UI 使用 React + open Shadow DOM + Tailwind CSS + Base UI（`@base-ui/react`），放入独立 `packages/ui`；`packages/web` 保留框架无关的编辑宿主、输入与薄 Renderer。已完成 G3 C01–C05 的现有能力接入，新建和其他缺失格式能力仍归 P10–P13。

### P10 DOCX 核心功能

用户结果：能够从空白文档创作，完成 GenOffice 的主要文档编辑操作，并通过 API 执行同样的修改、保存和输出。对应 G3 D01–D24 中的 P0 项。

按下列依赖顺序拆分，每项连同 UI、历史和保存交付：

1. 新建、富文本输入/粘贴、查找替换、字符/段落格式、样式和列表。
2. 页面/节、页眉页脚、表格结构/属性、图片与浮动图形。
3. 图表、数学公式、目录/字段、链接/书签、脚注/尾注与引用。
4. 本地批注与修订、保护、页面设计，补齐 PDF/图片/HTML/Markdown 和打印入口。

修改 `modules/formats/src/docx` 与相关 `modules/layout`，向上接 bridge、Wasm/client 与 UI。Office 编辑和分页算法按 ONLYOFFICE 优先、LibreOffice 次之参考。主题、浮动、列表、表格和审阅语义在核心；保留源包事务，不把 Tiptap 或 DOM 分页作为替代核心。

足够检查：选择包含本次特性的真实文件或可独立核对的输入，验证编辑、撤销和保存重开。改变分页/锚点时检查相关页面与定位；改变字段/资源关系时检查引用。只运行覆盖这些变化的检查。

### P11 XLSX 核心功能

用户结果：能够创建和维护常用工作簿，完成计算、格式、结构编辑与主要数据分析操作。对应 G3 S01–S24 的 P0 项。

1. 新建/工作表与行列结构、格式、合并/冻结、公式栏、选择性粘贴和基础填充。
2. 扩展常用函数族、名称/引用与依赖更新；细化未知公式的安全编辑范围，解决整本只读对日常操作的阻碍。
3. 查找替换、排序筛选、结构化表、条件格式、数据验证、分列/去重及保护/分组。
4. 图表/图片/绘图、透视表、切片器/时间线、批注/链接、CSV/TSV 与页面设置/打印。

计算、结构变更和序列化继续归 `modules/formats/src/xlsx`。修改引用时同步处理公式、区域、名称和对象锚点，按事务提交。图表沿已有绘制管线扩展；与其他格式出现实际共用需求时再提取共享实现。不能用保留缓存值宣称公式已可重算，也不能为解除只读而丢弃未知内容。

足够检查：围绕本次函数或操作核对独立结果；结构修改检查依赖更新、撤销和保存重开。透视表需验证数据变化后的刷新，图表需验证数据与保存关系。大表专项留到 P14，阻塞交互时提前处理具体瓶颈。

### P12 PPTX 核心功能

用户结果：能够从空白开始制作演示，管理页面、布局和对象，使用基本动画/媒体放映并保存输出。对应 G3 T01–T22 的 P0 项。

1. 新建与页面/章节管理、对象增删/复制、多选、几何、组合和层次。
2. 文本格式、主题/版式/母版、背景、图片、图形与连接线。
3. 表格、图表、简化 SmartArt 模板、公式、媒体、链接、备注/批注和页脚。
4. 放映与演讲者界面、基本切换/动画，补齐 PDF/图片输出和打印。

扩展 `modules/formats/src/pptx` 和实际需要的共享布局。动画时间关系与触发在核心；宿主提供时钟、媒体解码/播放和窗口能力，Renderer 只执行确定的视觉状态。浏览器内演讲者界面先交付，桌面多窗口等宿主能力在 P2 扩展。

足够检查：对象和母版修改验证保存重开、几何/继承及撤销。放映检查所实现的触发/顺序和资源结束释放。静态输出按当前对象覆盖声明；不能把近似动画播放扩大为全 PowerPoint 一致。

### P13 PDF 核心功能

用户结果：能够新建/整理 PDF，编辑可支持的文字和图片，完成批注、表单与真实脱敏，并进行常用输出和文本型 PDF 转 Office。对应 G3 F01–F22 的 P0 项。

1. 完整阅读 UI；新建、插入/替换/提取、合并/拆分、裁剪与页面尺寸。
2. 源文字和图片对象编辑，补字体/资源写回与编辑交互。
3. 常用批注、回复、印章/签名外观、水印/页码、表单填写与设计、真正遮盖删除。
4. 图片/打印/HTML/Markdown 输出；按 DOCX、XLSX、PPTX 分别交付 PDF 转换。

沿 `modules/formats/src/pdf` 的源对象图扩展，保持资源、页面引用和事务边界。PDF 转 Office 复用目标格式的新建与序列化，明确识别和重建的损失，不通过整页图片冒充可编辑转换。GenOffice 的 PDF.js/PDFium/pdf-lib 组合只提供功能证据；依赖或编解码器是否引入，按当前核心缺口单独决定。

足够检查：页面操作核对相关引用与保存重开；内容编辑核对输出文字/图片及未修改区域。脱敏必须确认目标内容不能从输出恢复，失败时拒绝输出。转换检查目标文件可编辑及声明的结构，保留识别告警。数字证书签名和 OCR 属于 P15；现有签名保护不能因此删除。

### P14 兼容与性能

用户结果：P10–P13 的操作能用于更广的真实文件，复杂和大文件的交互达到可用。对应 G3 各表的 P1 项。

按具体文件缺口推进：DOCX 复杂分节/浮动/表格/字段与字体排版，XLSX 更广函数/引用/格式规则与复杂结构，PPTX 图形/效果/动画/媒体和继承变体，PDF 字体/色彩/图像/透明与受保护输入。旧格式和加密输入逐条声明查看、转换和编辑范围；不自动承诺宏、任意 OLE 或全标准支持。

性能改进以实际瓶颈排序：核心增量布局/重算、可见范围计算、资源缓存与失效、Worker 传输、Canvas 执行和 UI 更新。能由共享核心解决的放入共享核心；Web 专属的调度、传输和表面复用留在 Web。沿 R0 增量修改，不新建另一套 Renderer 或先设计未知平台框架。

足够检查：兼容改动使用触发差距的样本及受影响的已有用例；性能改动记录同输入、同环境的前后结果，并检查文档输出和资源释放。没有实测依据时不设毫秒/体积门槛，不建立全量性能或浏览器矩阵。

### P15 次要与外围能力

用户结果：宿主可按需启用 AI、协作、Diff 与其他辅助能力。对应 G3 的 P2 项；这些能力仍属于完整目标，但不阻塞 P0/P1。

先实现有具体用户操作的接入：DOCX 段落比较、AI 调用已有命令、OCR、校对、Zotero 和数字证书等。每项单独确定输入、结果和平台依赖。AI 不能绕过核心校验；上传、模型服务、凭据与授权由宿主显式提供。OCR 不依赖隐藏的桌面辅助程序才能运行。

协作先定义文档事务同步、身份/权限、冲突、重连与持久化的实际需求，再选择同步机制。现有本地批注/修订不算实时协作完成；GenOffice 的 AI 命令注册表也不自动成为本项目插件协议。Diff 不默认包含自动合并，其他格式比较按具体需求扩展。

足够检查：验证本次接入的输入输出、失败和取消，以及其引入的数据完整性、权限或外发风险。没有服务时能继续使用本地核心功能。

### P16 跨宿主

CLI 和一个明确的非浏览器宿主复用核心完成真实读取、编辑和保存。作为最后一项需求，开始时确定运行时、输入输出及实际资源需求，再决定是否需要额外编译目标。数据操作和视觉输出分别验证；不先建设全语言绑定、native ABI 或通用运行时框架。

## 实施与完成口径

以上是阶段范围，不要求一次生成全部详细方案或一次完成整阶段。进入某阶段时，仅细化下一批用户操作及代码归属。G3 维护功能差距，SDK 文档维护职责，格式合同只记录已交付 API 与范围。

每个操作将核心、API、UI、保存和必要检查一起交付。完成 P0 核心功能不表示 P1/P2 已完成，也不把“有菜单”“能保留源文件”计为可编辑功能。文件读写、交互与视觉分别声明范围；执行细节见[测试说明](testing.md)。
