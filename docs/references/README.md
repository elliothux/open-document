# 文档与参考规范

项目尚未发布，当前有 0 个用户。文档直接服务当前功能开发，说明用户结果、实现范围和实际边界。

写文档、目标、方案和提示词前，读取 https://developers.openai.com/api/docs/guides/latest-model 原文。按任务采用其自主执行、指令优先级、简洁写作和适量验证原则。

用正向、具体的动作说明期望结果。先写要完成的操作，再写必要约束；安全、授权和文档保真保留明确边界。每个主题在已有权威文档中维护，按当前任务补齐内容。

产品与测试设计统一在父仓库维护；私有仓库保留测试实现、数据与详细证据。

## 状态与移动

`research` 表示仍待决定，`planned` 表示尚未全部实现，`implemented` 表示已实现且范围明确。检查通过只证明指定输入和环境；不能把计划或历史 PASS 写成当前能力。外部条件确实阻止继续时才使用 `blocked`。

完成方案后精简为交付结果与持久边界，再移入 `implemented/`。移动时保留编号，更新索引和入站链接，统一到新位置。

## 编号与命名

保留现有 P0–P9 产品阶段编号。研究用 G，Issue 批次用 I，通用渲染架构用 R。R 编号覆盖各格式与平台的共同设计，具体落地按产品阶段推进。标题使用大写编号，文件名使用小写编号和英文 kebab-case。运行、修复和子任务更新所属方案。

## 内容与权威

每个主题只维护一个入口。路线图说明阶段，SDK 文档说明职责，格式文档说明 API 与保真，阶段方案说明当前交付。其他文档链接到对应入口。

文档保留结论、支持范围和影响下一步的限制。逐次计时、完整 hash 清单、命令输出和修复过程留在私有记录中。上游依据使用具体 GitHub 文件链接，优先固定 revision。

## 技术写作

以下规则整合原 Hai Simplified Technical 技能中适用于本项目的内容。日常回复遵循根 AGENTS 的语言规则；这里补充技术文档、API 说明、代码注释、错误信息和提交说明的写法。

- 沿用代码和现有文档中的术语，一个概念使用一个名称。首次解释缩写；文件名、标识符、命令和原始输出保持原样。
- 写清动作和执行者。例如，把“进行输入校验”改为“核心校验输入”，把长定语拆成动作与条件。
- 明确区分要求、建议和能力。中文用“必须”“建议”“可以”，英文用 `must`、`should`、`can`；操作步骤直接写动作。
- 按顺序编号操作步骤，一步说明一个动作。先写前提和条件，再写命令及预期结果；命令注明工作目录和必要输入。
- 对实际存在的数据丢失、不可逆或外发风险，在对应步骤前说明操作要求和后果。普通说明保持简短。
- 改写时保留事实、条件、例外、疑问和结论强度。缺信息时标明未知；仅在缺失信息阻止读者操作时使用待补项，数值依据实际证据填写。
- 测量数字附带输入、环境、版本和日期，区分实测结果与计划。已有证据直接引用，缺失证据如实说明。
- 使用文档所属语言的标点，保持术语、引号和单位一致。日期写清年月日，记录中使用 `YYYY-MM-DD`。以准确、自然、易读为准，直接审阅文字后交付。

## P 编号方案的验证合同

方案说明用户操作、当前范围、代码归属，以及证明可用的输入和检查。把未来能力放在对应后续阶段。自动化检查围绕功能结果和实际风险设计；文案、标签、界面配色及文档修改直接审阅。保存/生命周期变更补保真与恢复检查。

以功能交付为完成目标。实际卡死、无法交互或资源失控时做最小诊断；性能专项与发布工作留在后续。具体数据与预期由现有私有测试库维护。

## 证据与检查

区分已实现、未验证、失败和不支持。用私有 case/run 标识定位详细证据。文档变更完成 `git diff --check`、受影响链接、命令与状态检查后交付。
