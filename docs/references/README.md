# 文档与参考规范

本文件是 Open Document 文档组织、编号、生命周期与证据规则的唯一权威入口。规则参考 open-compute 的文档规范，移除其 workerd、Cloudflare、站点和发布工具专属约定。导航见[文档索引](../README.md)。

## 文档位置

| 位置 | 内容 |
| --- | --- |
| 根 `README.md` | 产品介绍、当前状态、文档入口和许可证，不承载技术细节 |
| 根 `AGENTS.md` | 开发协作、变更与验证约定，引用本规范而不复述它 |
| `docs/*.md` | 待决研究、仍需实施的需求和方案，使用编号 |
| `docs/implemented/` | 已完成需求的精简结果、持久边界和当时证据 |
| `docs/blocked/` | 外部前置条件阻止继续的事项，写明恢复条件 |
| `docs/references/` | 持续维护的合同、接口、开发、测试或参考资料 |
| `docs/references/runbooks/` | 确有需要时建立的操作手册；当前不预建 |
| 根 `references/` | 独立上游源码研究副本，不属于文档目录或构建依赖 |
| 根 `.temp/<purpose>/` | 本地缓存、原始输出、运行 artifact 和保留的失败证据，不提交 |

不要为单篇文档另建 `research/`、`plans/` 或专题目录；只有出现真正独立的子项目和多篇文档时才增加专项目录，并在本表定义职责。按生命周期划分的目录不受此限制。

产品路线、阶段实现方案、架构研究和测试设计统一在父仓库 `docs/`。`test-lab/` 只保留测试代码、数据、具体预期、执行工具、技能和原始证据，不维护 `docs/`、副本或重定向。每份阶段方案同时描述用户结果、实现归属、前置依赖、交付步骤与验收；不能用测试清单代替产品方案。README/AGENTS 只指向统一入口。

## 状态与移动

- `research`：证据正在收集或方案尚待决定；调查完成不等于建议获批。
- `planned`：最终行为已决定，代码尚未全部落地。
- `implemented`：实现已落地，当前支持范围和限制已说明。
- `verified`：指定输入与环境下的检查成功退出；这是证据标记，不是永久状态或单独目录。
- `accepted limitation`：已知限制及影响被产品明确接受，不是文档作者自行豁免。
- `blocked`：外部前置条件确实阻止继续，并有阻塞证据、影响及恢复条件。

有待决定或待实现内容时留在 `docs/`。实现完成后先删除实施过程、备选和完成的 TODO，再把精简结果移入 `implemented/`；它不是计划全文的归档库。

一次性 G 调查只有在调查问题收敛、结论及未决事项明确归属后才可收尾；完成目录只保留调查结果与证据，不把候选设计标为产品已实现。当前仍服务待决选择的 G0 保留在活动目录。

仍需修复的缺陷、功能缺口和 TODO 留在活动方案；已接受限制归所属实现或维护文档。缺少本地工具、尚未验证或任务困难，不自动构成外部阻塞。短期内没有发布计划，不预建发布文档目录或版本说明规范。

移动文档时编号不变，同步更新索引、入站链接和实际存在的脚本引用；不保留 redirect、stub 或旧副本。

## 编号与命名

需求、研究、实施和阻塞文档必须使用编号；标题使用大写编号，文件名使用小写编号加英文 kebab-case 描述。

| 前缀 | 范围 | 示例 |
| --- | --- | --- |
| `P` | Open Document 产品阶段或功能方案 | `p1-sdk-foundation.md` |
| `I` | Issue 实施批次 | `i0-import-errors.md` |
| `G` | 一次性调查、POC 或能力验证研究 | `g0-foundation-review.md` |
| `Q` | 质量专项 | `q0-quality-baseline.md` |
| `R` | 跨既有阶段的架构重构 | `r0-session-ownership.md` |

示例不表示已经创建或实施相应阶段。open-compute 的 `W` 属于 workerd 子项目，本项目不沿用或重新解释为 WASM。

- 每个前缀独立编号，从 0 开始。新增前搜索所有活动、完成、阻塞文档及索引，取该前缀已分配主编号的下一个，不复用旧编号。
- 子阶段使用所属主编号，例如 `P2.6` 对应 `p2-6-<topic>.md`；主文档与子阶段保持职责区分，不复制内容。
- 同一事项从活动目录移到完成或阻塞目录时，保留编号与文件名；不要因状态变化另开编号。
- `I` 是实施批次编号，不必等于 GitHub issue 编号；正文列明关联 issue。
- `R` 只用于替换横跨既有阶段的权威架构，普通整理、功能和修复归所属 `P`、`I` 或 `Q`。
- P 文档按当前实施顺序编号；平台优先级直接写“浏览器优先、跨宿主后续”，不复用 P 编号表示平台。
- 各目录的 `README.md`、持续维护的 `docs/references/**`、根项目元文档不使用阶段编号。
- 新增或移动后检查上述编号目录，不留下无编号正文，也不让同一编号同时出现在活动与归档目录。

2026-10-08 按用户要求统一重编号：已实现的工程阶段为 P0，原目标/选型文档为 P1，并承接原 P3.1 的前置文本探针；P3 子目标从段落开始顺排。当前文档、引用与机器清单同步，历史运行报告保留原编号，不回写旧证据。之后新增阶段从未分配编号继续。

## 内容与权威

先写用户结果和会影响以后修改的边界。活动方案按需要补目标、非目标、约束、决策、状态归属、失败语义和验收证据，不为凑模板写空章节。

每个合同只保留一个权威位置：产品与阶段行为归所属方案；当前接口与支持面归源码、机器可读合同及维护文档；完成文档只记录当时实现结果，不覆盖当前合同。根 README 不重复技术选型、架构表、运行命令、测试记录或源码入口清单。

不要保留独立的 qualification、acceptance、Gate、test-plan 文档。验证条件写入所属方案，实际结果留在所属结果或维护资料；测试代码拥有可执行的用例细节。

`implemented/` 只保留用户可见结果、稳定边界、实际验证和接受的限制，不保留调研全文、逐文件任务、实施顺序、穷举 schema/API、完整测试矩阵或完成的 TODO。过期内容删除前检查是否有仍然有效且唯一的合同或证据；Git 保留已提交历史，未提交资料不能假设可从 Git 恢复。

## P 编号方案的验证合同

从 2026-10-11 起，所有新增或实质修订的 P 编号方案（含子阶段）必须在实施前写明本阶段的验证合同。不能只写「补充测试」「保证兼容性」「性能良好」，也不能只链接公共流水线。每项产品承诺都要能追溯到输入、操作、独立预期和通过条件；测试设计与产品设计一起完成，而不是功能写完后再补。

| 必须明确的内容 | 方案需要回答的问题 |
| --- | --- |
| 功能与支持边界 | 本阶段承诺哪些输入、操作、输出和错误行为？读取、保留、显示、编辑、转换分别支持到哪里，哪些明确不做？ |
| 测试路径与覆盖 | 哪些由 MoonBit 算法测试、正式 library 包 API、真实 browser/Worker 或外部工具检查？列出成功、失败、边界和受影响回归用例族；涉及生命周期时覆盖销毁、恢复和状态保持。不能以 native/mock 结果替代浏览器证据。 |
| Fixture 与真实文件 | 每个用例族使用什么原子、真实回归/业务、畸形或超限输入？写明候选来源、要覆盖的特征、取得/生成方式、许可与隐私检查、固定版本/hash 的方式，以及已具备或待准备状态。涉及文件兼容性的能力必须包含真实文件，不能只有自建样本；缩小反例不能替代原文件回归。 |
| 独立预期与判定器 | expected/golden 来自哪个标准、上游断言、参考引擎或人工核验？固定哪些引擎、字体、环境和 profile？如何验证判定器会抓住错误，参考冲突如何处理？不能仅用 SDK 自身输出生成答案。 |
| 兼容性与保真 | 明确格式/profile、Microsoft Office 目标平台/版本及适用的宿主/浏览器范围。按能力选择模型、导出结构、内容、布局/像素和参考应用重开检查；保存能力覆盖 no-op、指定编辑、重复往返、未知内容及非目标内容保持。不支持的特征是拒绝、保留还是明确降级，必须写清。LibreOffice/ONLYOFFICE 差分不等于微软兼容性证明。 |
| 性能与资源 | 选哪些代表性文件/规模，测哪些核心和端到端区间、冷/暖状态、体积与资源预算？写出指标、单位、环境、基线、重复采样和退化规则。尚无可靠数字时给出校准步骤及形成门槛的条件，不能虚构 SLA；无法测量的项不能填零或算通过。 |
| 执行与反馈 | 明确已有执行入口、需要新增的 runner/case/manifest 工作及其归属，区分选测和完整验收。失败报告应能定位输入、操作、expected/actual、源码/产物/环境和复现步骤，并保留 Agent 继续修复所需的差异、日志和原文件；不得把待实现的验证入口或尚未取得的证据写成现成能力。 |
| 验收与停止条件 | 哪些 case/surface/profile 必须全部通过？零执行、漏测、缺参考、超时、基础设施错误如何阻止验收？本阶段有哪些前置缺口、需确认事项和停止条件？修复后跑哪些相邻能力回归，谁批准 golden/阈值变化？ |

推荐在所属 P 方案中用一张精简映射表落实上述要求：`能力/操作 → 测试路径与用例族 → fixture 来源及准备状态 → 独立预期与兼容目标 → 性能/资源条件 → 验收证据`。表格可以拆分，但不能漏掉承诺；无需为每项机械建立重复章节。

不适用项必须写原因。例如纯字体阶段使用真实字体和文本向量，不强制引入尚未支持的 Office 文件；不涉及保存时不虚构往返测试。子阶段可明确继承父方案的具体合同，只写新增或变化部分，但必须覆盖自身交付，不能笼统写「同父方案」。

设计时 fixture、参考环境或性能基线可以尚未就绪，但必须有具体来源、准备步骤、归属和完成条件；将它们作为对应能力验收的前置项。不能以「以后补」代替设计，也不能在缺少必需证据时宣告阶段完成。归档时按现有规则精简为支持范围、实际验证、未支持范围与明确接受的限制，不回写历史通过结果。

方案文档只记录覆盖意图、来源计划和验收合同。测试代码、fixture 字节、具体 expected/golden、可执行清单及运行报告仍在私有 `test-lab/`，不复制到公开方案。通用执行规则引用[测试说明](testing.md)，数据管理引用[语料管理](corpus.md)；[G2](../implemented/g2-test-pipeline.md)记录本地流水线建设结果，不替代各 P 的具体验证设计，也不自动授权新基础设施或扩大产品范围。

## 证据与检查

- 事实、研究建议、已批准决定与实际实现分别表述；未运行、不支持和失败不能写成通过。
- 测试记录注明日期、源码/工具链版本、输入、环境、命令和结果。历史 PASS 只证明当时输入；零用例、mock 或 native 结果不能冒充真实浏览器 WasmGC 验证。
- 原始长日志与失败 artifact 留在 `.temp/` 或 CI；长期文档只记录结论和定位标识。必须原样保存的生成报告须说明原因，不改写历史证据。
- 本地链接只指向随项目维护的文件，使用相对路径。禁止引用被忽略的根 `references/` 或相邻项目的研究副本，即使本机存在也不能作为文档入口；上游源码证据直接链接 GitHub 的具体文件或目录，优先固定 commit。`docs/references/` 是受版本管理的维护资料，不受此禁令影响。
- 参考副本不是发布或测试依赖，不保证存在。历史本地验证记录保留命令、固定 revision 和结果，不把本机路径当成可复现入口，也不假造验证。
- 文档修改至少运行 `git diff --check`；同时检查未跟踪新文档的空白、链接与锚点、编号唯一性、目录、索引、状态和命令真实性。纯文档变更不要求编译 SDK 或参考仓库。
- 当前没有独立文档校验脚本或发布流水线；不得引用尚未存在的入口为已建立的 Gate。
